## E1｜whisper.cpp token 概率 `p` 与错字相关性（Qwen，2026-11-02）

- **commit**：`14aad46`（不涉及本仓代码改动，取 ASR 侧数据）
- **环境**：whisper.cpp 1.9.5-dev，`build-vs/bin/Release/whisper-cli.exe`，模型 `ggml-large-v3-turbo.bin`，后端 Vulkan / AMD RX 6800 XT，`-l zh -t 8 -fa`
- **数据**：B 站 4 条视频（1 条新闻播报 + 3 条由 popular 接口随机抽样，时长 103–223 s），产物在 `asr/`；音频统一为 16 kHz / 单声道 / pcm_s16le
- **标注**：人工，A 类同音错字 35 token、B 类整段幻觉 183 token、文本 token 合计 1,759（另剔除 `[_TT_*]`／`[_BEG_]`／空格 token 239 个）
- **结果**：
  | 指标 | 值 |
  |---|---|
  | A 类 mean/median `p` | 0.6724 / 0.7430 |
  | 正确 token mean | 0.9447 |
  | B 类 median | 0.9921（70% 的 B 类 token `p≥0.98`） |
  | AUC 错字 vs 正确 | 0.874 |
  | AUC 幻觉 vs 正确 | 0.672 |
  | 段级 AUC（min-p / mean-p） | 0.886 / 0.822 |
  | 最优二值门限 | `p<0.5`：召回 34.3%、精确率 21.1%、F1 0.261 |
  | `p≥0.99` 的错字占比 | 8.6%（3/35） |
  | 特殊 token mean `p` | 0.4266（最低 0.0008，必须剔除后再设阈值） |
- **结论**：`p` 有排序价值、无判决价值；幻觉段呈「段首单个极低 p + 后续模板化高 p」的形态，均值判定会误判为可信。
- **复现**：`python asr/_p_report.py stats`（标注 `asr/_errors.json`），报告 `asr/P_CONFIDENCE_REPORT.md`

### 两处改动（均与参考冲突）

```text
BV1yQfWYaEVo.txt 5284..5286  "有信" -> "微信"  fuzzy D=1 score=0.0362944 fC=3 fO=0
  上下文：对 DLSS4 足够有信心        输出：对 DLSS4 足够微信心
BV1fhhP6xEMp.txt 4234..4236  "有信" -> "微信"  fuzzy D=1 score=0.0362944 fC=3 fO=0
  上下文：我对 O3 的实机也还是很有信心的  输出：…很有微信心的
```

两篇参考正文均保留 `有信心`，因此 2/2 为误改。

### 根因链路（已核实）

1. 分词约为 `[足够][有][信心]` / `[很][有][信心]`；`有` 是单字未知 token，窗口从已知词 `信心` 借出 `信`，留下残片 `心`（当前边界许可允许残片一字）。
2. `data/pinyin_dict.txt`：`有 = you3,you4,wei3`；`信 = xin4,shen1`；`微 = wei1`。v1.2.2 已把**候选侧** `微信` 限制为词表声明的 `wei xin`，但**输入侧** `有` 仍可用 `wei3`。
3. 于是 `有信(wei3 xin4)` vs `微信(wei1 xin4)` 仅差一个声调，D=1。
4. `有信` 不在 `word_freq`（fO=0），`微信` 词频 3（fC=3），R=ln4=1.3863，score=1.3863−0.65−0.70=**0.0362944 > 0**，`context_bonus=0`，恰好过门限。

### 结论

- v1.2.2 的候选侧修复有效：`BV1ghec66Eau` 的 `微深→微信` 已消失（0 改动）。
- 但同类问题转移到**输入侧稀有异读 + 边缘借字窗口**：自然 ASR 语料上复现 2 次，不能视为个例。
- `fO=0 + fC=地板3 + D=1 → ΔS=0.0363` 的常数通道在自然语料上得到实例（与 Qwen H1 方向一致）；它对假阳分布的贡献占比仍未统计。
- 参考完全一致 2/10 主要受**漏召回**影响（如 `直接暴→支付宝`、`为新→微信`、`化微→华为`、`直到爆→支付宝`），不能把该数字当精确率。

## E6｜CyIME 词表/读音机制调研 + 罕见读音惩罚的可迁移性实测（Qwen，2026-11-03）

- **commit**：`14aad46`；被测二进制 `build-probe/text_clean.exe`（E2/E3 同一个）
- **上游**：<https://github.com/Cyletix/CyIME> @ `main`，**GPL-3.0**（GitHub API 未检出 license，实为根目录 `LICENSE` = GPLv3）。参考文件按 contents API 取回，含 sha 备查，副本仅放在 `log/cyime/`（gitignore）：
  `tools/ime_lab/reading_table.py` a55543b2｜`tools/ime_lab/lexical_weights.py` 767a5fe1｜`scripts/merge_base_dict.py` 9054d204｜`docs/development/pinyin26-word-model-20261018.md` d104a530
- **测试数据**：`datasets/CTCDataset/cscd-ns/test.jsonl` 前 2,000 句（等长句对），词表用 E3 的 `datasets/ctc_probe_lexicon.txt`（6,553 条，train 派生）
- **读音证据表**（自建，不用上游数据）：`data/word_freq.txt` 的词按 `pypinyin 0.55 (heteronym=True)` 展开全部被证实读音，权重取该词频次 → `(字, 读音) → 频率`，得 **8,131 个格子、覆盖 5,437 个字**；惩罚量 = `ln(max(evidence,1) / 该字主读 evidence)`（与上游同形式，独立实现）
- **还原方式**：`-v` 诊断的 span 偏移**不可用**（137 条里仅 2 条与输入码点吻合）→ 改由 stdout 与输入逐位 diff 还原「原文片段 → 替换片段」；因 Replace 保持长度，连续差异 run 即被改写区间
- **结果（同一样本内）**：还原改写 3,921 处、改动字符 5,839；按可读证据分类后 fp=5,652 / tp=61（虚词统计那次为 fp=5,678 / tp=62，差异来自「找不到兼容读音」的字符被跳过，分母不同）
  | 判据 | 数值 |
  |---|---|
  | 改动位置中「读音无任何词级证据」占比 | **2.4%** |
  | AUC(读音稀有度；fp vs tp) | **0.512** |
  | τ=-1.0（上游默认） | 杀 13.4% fp，同时杀 **27.9%** tp |
  | τ=0（只允许被词表证实的读音） | 杀 27.2% fp，杀 63.9% tp |
  | fp 最高的字 | 的 691｜是 134｜在 126｜被 85｜和 74｜了 68｜也 67｜有 62 |
  | fp 集中度 | 前 20 个字占全部 fp 的 **31.6%** |
  | 对照规则：含高频虚词且整串无词频 → 否决 | N=50 杀 44.7% fp / 29.0% tp；N=100 杀 52.0% / 38.7% |

  高频字表由文本自身 unigram 构造（CTCDataset `target` + `whisper_txt` 正文，5,257 个不同字；前 **170** 个字即覆盖 50% 文本量），不使用标签信息。
- **结论**：
  1. **读音惩罚作为硬门不成立**：AUC 0.512 等于没有区分力，且每个 τ 下的 tp 损失都大于 fp 收益。原设想（H2）被自己的数据否证。
  2. 但**数据结构应当迁移**：本仓现在是 `字 → 读音集合`（无频率、无词级上下文），上游是 `(词, 读音) → 频率` 的行级多读音表。后者才允许「按词条具体读音的相对频率」这种用法；本仓的正确用法是把读音选取上下文化（依切分结果限定候选读音）+ 惩罚进 ΔS 作软项，不作否决。
  3. **fp 的真实主因不是读音而是频率口径**：`fO=0` 用整串词频判定，虚词两字组合天然无词条 → 一律被当作「不成词错字」。因此优先级仍是 D4（分数口径）与 D2（别名权威化），虚词/字频合法性是新增的高收益候选手段（但见下述局限）。
- **局限**：tp 基数只有 61–62，τ 与 N 的百分比在小样本上不稳定，**虚词否决规则需在全部 test 划分复测后再决定是否采纳**；证据表依赖 pypinyin 的词表覆盖度，未被其收录的合法异读会被误判为无证据（2.4% 是该口径下的占比，不是真实罕见读音总量）。
- **复现**：`python tools/reading_freq_probe.py --only cscd-ns/test --limit 2000`

- **候选硬否决规则的选择性**（杀 fp 比例 / 伤 tp 比例 / 选择性）：

- **根因（三层，均有代码位置）**
  1. **判据单一**：原文合法性 = `WordFrequency::count(span)` 精确查询（`src/word_frequency.cpp:130-133`，未命中返回 0），叠加 `Vocabulary::contains` 只作否决（`src/text_cleaner.cpp:300`）。没有字频、构词完整性或 bigram 层。`fO=0` 在中文里覆盖 83% 的片段，因此它标识的是「没查到词」而不是「像错字」。
  2. **两侧口径不对称造出零证据改写区**：候选侧频率被地板抬高 `kHotwordFrequencyFloor=3`（`src/text_cleaner.cpp:341-342`），原文侧用裸 `count()`（`:306`）。于是 `fO=0 ∧ d≤1 ∧ fC≥3` ⇒ ΔS = ln4 − 0.65 − 0.70 = **0.0363 > 0** 恒成立，改写不需要任何正向证据；E7 的 fp:tp=17.7:1 就是这个区域的体积。`d=2` 需 `fC≥7`，所以高频目标词（华为 373、银行卡 216）在任何阈值下都能改写远距离片段（E2/E3 一致）。
  3. **第二个频率源存在却被显式弃用**：`data/dict.txt` 每行自带频率与词性列，而 `include/text_clean/vocabulary.h:6-7` 写明「Membership only… Counts ignored」。另外 `WordFrequency::add_word` 对重复行取 `max()` 而非累加（`src/word_frequency.cpp:121-123`）——融合语义未声明，属第三种隐式口径。
- **结论（供排期）**：先把「原文是否合法」从单一词频查询换成 **字频 + bigram PMI + 构词完整性 + 词典命中** 的组合证据，并消除地板不对称；否则任何别名权威化或区间 DP 改动都会被这 83% 的假前提淹没。

## E10｜构建/测试环境排查：MinGW 升级与「5 项失败」的真相（Qwen，2026-11-03）

- **工具链**：升级前 gcc 13.2.0-2 / binutils 2.41-2 / crt-headers-winpthreads `-git` 11.0.0；升级后 **gcc 16.2.0-6 / binutils 2.47-4 / crt、headers、winpthreads 14.0.0**。`-git` 已拆名，只能整机 `-Syu`；两次假失败源于限速中断（475 MB 事务）与残留 `db.lck`，修法是 `pacman.conf` 加 `XferCommand = curl --retry 10 --retry-all-errors -C - --speed-limit 512 --speed-time 120`、`ParallelDownloads` 5→2（备份 `etc/pacman.conf.bak-before-mgw`）。判定升级是否生效只认 `pacman -Q` 与 `g++ --version`——重试脚本里混入已删除包名会让整笔事务被拒而末尾命令 exit code 仍为 0。
- **`CMake compiler identification unknown` 的根因**：`libstdc++-6.dll` 由 `D:\Git\mingw64\bin`（2023-08，gcc13 时代，PATH 第 5/9 位）先于 `D:\msys64\mingw64\bin`（2026-10，第 34 位）解析，导致 `cc1/cc1plus` **STATUS_ENTRYPOINT_NOT_FOUND `0xC0000139`** 静默失败。构建前 `export PATH="/d/msys64/mingw64/bin:$PATH"` 即恢复；用户已在系统 PATH 层面修正并验证。
- **结论：历史 5 项「MinGW 失败」是本沙箱环境的假红，与编译器版本和代码无关。** 变量隔离（同一字节 exe 逐一控制变量）：映像位置 × CWD 的 2×3 矩阵全部通过；差异真正来自**由沙箱 shell 在工作区内直接 `gcc` 产出**的 exe。决定性一行：`build-tt\tw.exe … Mandatory Label\Low Mandatory Level:(I)(NW)`。Low IL 进程不能写 `%TEMP%`（`fopen` errno=13）→ 夹具建不出来 → `load_file` 报 `cannot open word frequency file` → 5 项失败，其中 2 项因 size=0 下游越界 SEGFAULT。MSVC/常规终端产出 Medium IL 故看不到。
  - 附带更正：本次排查中一度把根因写成「仓库根 `Everyone:(CI)(DENY)(DC)` ACE」并建议 `icacls /remove:d`——**该归因错误，建议撤回，ACE 保持原样**。那两条 ACE 源自 `D:` 卷根（`D:\` 与 `D:\text_clean` 各 2 条，`data/`、`AppData\Local` 为 0），属禁止删除子项的保护控制。agent 进程为用户 `Lin` 且未提权（`IsInRole(Administrator)=False`）。
- **两种已验证的非破坏性做法**（都不动安全设置，均 **18/19**，唯一失败是 E9 的 `test_cli_context`）：

## E11｜离线模拟：把 AC Keep 锁定范围扩到「完整词边界」的理论收益（Qwen，2026-11-03）

- **问题**：不改代码、不扩词库，只测算「AC 锁定范围变大」这条路线能挡掉多少 E8 假阳、误伤多少真修复、净收益多大。
- **机制依据**：`select_exact()` 把每个 AC 命中 span 标成 `LockedByAc`（src/text_cleaner.cpp:193-216，选择规则=最早起点最长词），`scan_run` 对任何与 locked 字符重叠的窗口直接 `continue`（src/text_cleaner.cpp:298）。所以锁定是**位置硬否决**，与 ΔS 无关；`overlaps_locked` 也顺带切断跨锁字的 run。

- **误伤机制（实测例子，freq≥1000 锁）**：`啦肚子→拉肚子`(6) 锁=肚子、`前列缐→前列腺`(5) 锁=前列、`唐尿病→糖尿病`(4) 锁=病人、`这样以来→这样一来`(4) 锁=这样、`小时后→小时候`(3) 锁=小时——错字就嵌在合法词内部或跨界，锁字即锁死错字。同期挡掉的代表假阳：`有什么→为什么`(630) 锁=什么、`的方向→地方性`(347) 锁=方向、`么药→麻药`(296) 锁=什么。
- **重放偏差的定量校准（重要）**：同一离线方法重放「d≤1 距离上限」给 det_P 0.1924 / det_TP 6,079 / 整句 1,692，而 E8 真跑 `--max-distance 1` 给 0.2177 / 10,777 / 2,602。差异全部来自离线重放无法建模**被释放的候选**（分量裁决换人）。故本 E11 的绝对值是**保守下界**（tp 低估约 44%、det_P 低估约 12%），变体之间的相对排序不受影响。
- **叠加口径**：`dict ≥2 字 freq≥1000` 锁 + `d≤1` 上限（同一离线口径）→ 窗口 fp:tp **2.78**、det_P 0.1924→0.2617、整句 +95、留 94.9% tp。这是本次唯一跌破 D-8 3:1 的组合，但两个成分都是硬否决，且 8.9% 的 gold 位置被永久封死。
- **结论**：
  1. 路线**有正收益但不足以完成 D-8**：最好比例 11.71→8.04 要付 20% tp + 25.4% gold 封死；稳健工作点（freq≥1000）是 det_P +12.9% 相对、整句 +9.7%、tp −5.1%。
  2. 最大正项在**整句**而非窗口比例：挡住「改错了」的改写使精确匹配句子 +136——这是「少改」带来的，不是「判得更准」。
  3. 结构上限由距离通道决定：锁只碰 d=2 的 7.6%，而 d=2 占 fp 的 61.6%。想动 fp:tp 必须动候选生成/距离准入，不能靠位置锁。
  4. **硬约束（给 D-2 别名权威化）**：lexicon 含别名时该表就是错词清单，作锁集合会杀掉 53% 的 tp 并让比例反向恶化；别名只能走 replace，绝不进 Keep 锁。
  5. 锁把「窗口须落在词边界内」变成硬约束，与缺陷 D5（区间 DP 重叠选择）改的是同一处结构；两者若都做，收益会互相覆盖，实施顺序需先定。
