## 轮次 3｜单字拼音补齐（2026-11-06，园长指示：热词频率与 mask 先搁置）

### 做了什么

园长指示用 pypinyin 补单字拼音，并允许联网。实测后**不需要联网**，因为本地已有 pypinyin 生成物。改写了 `tools/normalize_dicts.py`：

1. **修了一个真 bug**：CC-CEDICT 的谚语/对联类条目在方括号里用**逗号分隔多读音**（`[yi1bu4zuo4,er4bu4xiu1]`），轮次 2 的解析把它们拼成了一串。现在按逗号拆成 `|` 分隔的多读音。验证：`一不做，二不休` → `yi1bu4zuo4|er4bu4xiu1`。
2. **统一了读音写法**：`lu:` → `lv`、`ü` → `v`、去 `·`，与项目既有约定（`gen_pinyin_dict.py` 注释 "v 表示 ü"）一致。验证：`一律` → `yi1lv4`。词级 110,814 行中有 **1,755 行**因这条规范化被改写。
3. **单字表改为两源合并**：CC-CEDICT（词级库里的单字条目）+ `data/old/pinyin_dict.txt`（pypinyin **0.55.0**，`heteronym=True`，MIT）。新增两列可追溯：`sources`（pypinyin/cedict/两者）与 `agreement`（可靠度标记）。

### 二、词频表调研（园长问：国内有没有更新更全的）

先量自己手上的：`jieba dict.txt`(2013) 与 `SUBTLEX-CH-WF`(2010) **都不含微信/抖音/点赞/UP主**；本地 THUOCL 两份子库（成语 8,519、地名 44,804）也没有。这就是 fC 只剩地板值的根因。

候选逐个实测，结论分三档：

**已排除（实测）**
* **中央研究院现代汉语词频**（HuggingFace `zetavg/tw-sinica-corpus-word-frequency`，165,505 词条，2023-05 发布，29MB JSON 已下载）：实测是**繁体**语料（含"们/这/个/说/话"的词条 0 条），且微信/腾讯/支付宝/直播/点赞/手机/人工智能 **18 个测试词里 17 个缺失**，抖音词频仅 1。不适用。

**可用且已验证（推荐）**
* **rspeer/wordfreq**：本机 `py -m pip install --user "wordfreq[cjk]"` 装好并实测，**10 个目标词全部有频率**（zipf 分值）：微信 4.85、抖音 3.23、腾讯 4.49、支付宝 4.02、字节跳动 2.34、银行卡 3.81、转账 3.65、验证码 3.20、敏感词 3.39、华为—（另测直播 4.90、视频 5.50、手机 5.42、人工智能 3.78）。多源合并（维基百科/字幕/社交媒体/图书），许可：代码 Apache-2.0、**数据 CC BY-SA 4.0**（share-alike，对外发布派生词库需署名与同许可）。可离线导出：`top_n_list('zh', N)` + `zipf_frequency` 能生成我们的 TSV。
  * **量纲提示**：它给的是 zipf 指数（log10 尺度），不是次数。换算关系 `ln(fC/fO) = ln(10) × (zipfC − zipfO)`，即**换到 zipf 域后 ΔS 的频率项变成两值直接相减 ×2.3026**，反而能把"词频计数 vs 字符独立期望"两套口径统一到同一尺度（wordfreq 也提供单字 zipf），顺带解决旧账里"三种频率口径并存"的问题。
* 环境副作用要报告：为验证 wordfreq，我用 `py -m pip install --user` 装了 `wordfreq[cjk]`（含 jieba），装到 `C:\Users\Lin\AppData\Roaming\Python\Python314`。**mingw64 那个 python 没有 pip，未受影响**。要撤销：`py -m pip uninstall -y wordfreq jieba`。

**值得追但还没拿到数据（需登录/许可不明）**

5. 我自己本轮踩的坑（都已修正并在脚本里留注释）：`O / 'funnel_%s.json' % ARM` 运算符优先级导致文件名错；把"已改对"放在判因瀑布后面，导致薄分通过的实例被误记成 S5（改成先判通过）；S2 判据初版写成无意义的复合条件，改成显式复刻索引必要条件；E026 之前几版把 S1 与长度混在一起，现已拆成 S1a/S1b。

## 2026-11-08｜E027 首音节保护确认 + 基准冻结（Astra）

做了什么：按指令零改动确认保护是否真在干活。核对执行点、测拦截面、做开/关 A/B，并把七篇结果冻结成基准。二进制没重建（仍是 M3 删除后的 b849f0b7b5ef9b94，与 E026 记录逐字节相同），词库/公式/参数一律未动。

结果如何：默认配置 Z1 = 64 改对 / 87 误改 / 2047 总距离；控制臂 Z2 = 147 / 100 / 1977。关掉保护：Z1 → 66 / 117 / 2075，Z2 → 149 / 130 / 2005。两臂新增的 19 条编辑一模一样：误改 16、错到错 2、改对只有 1，全部 d=2。**保护确认生效、确认是净收益、确认保持启用。** 拦截面：51,344 个可作窗口起点的汉字位通过 71.22%、拦下 28.78%，first_bases 150 个音节。

发现什么问题：
1. **这项保护其实有三个执行点，诊断开关只盖住两个**：`:303` 起点门与 `:311` 索引 `require_first` 会跟着 `--no-first-syllable-gate` 关，`:283` 边缘窗口起点门不看这个开关，任何情况下都在生效。本轮承诺不改代码，所以没法把它一起关掉做完整 A/B；这意味着上面测到的保护强度是**下限**，不是全量。已在记录里写明，下一步若要做完整消融，需要园长先批准"把开关覆盖三处"这一处代码改动。
2. E023 当年测得这道门拦 93.05% 的窗口起点，现在只拦 28.78%。原因不是代码变了，是 `first_bases` 从 10 条词表长到 150 个音节——同一道门在不同词库规模下含义完全不同。**今后引用"首音节门拦掉多少"必须同时报词库规模**，否则数字会互相打脸。
3. 关掉保护后有 1 条编辑反而消失，说明保护除了直接拦候选，还会改变竞争格局；这类二阶效应无法靠单点 A/B 归因，先记下不解释成收益。

基准与规矩：生产默认 64/87/19/2047、控制臂 147/100/27/1977、不纠错 0/0/0/2024 已写入 `results/baseline.json`；README 里定了下一步的对照规则——任何改动必须同时报与基准的差值、开/关保护两组、实例级漏斗各关变化，缺一不宣布改善。仍未提交未推送。

## 2026-11-08｜E029 单字纠错实测（Astra）

做了什么：加 `--target-char-freq`（默认关，单字目标词改查字频表），再造一份只看读音表和字频表、不看真值的单字候选池（带调读音 1,507 组、每组字频前 10，去重 5,867 个单字目标词，放在 build/e029_data 副本里，正式 data/ 未动），跑七臂对照，逐个条件只动一次。默认输出与基准 7/7 逐字节相同，ctest 24/24。

结果如何：全开臂 R6 = 95 改对 / 549 误改 / 145 错到错 / 2478 总距离，比控制臂 R5（147/100/27/1977）差 501，比不纠错（2024）差 454。单字编辑 637 处：对 48（7.5%）、把对的改错 457、把错的改成另一个错 132。估算的方向对（单字很不划算），但代价被我低估了 2.4 倍。

发现什么问题：
1. R3（单字池+窗1+开关，但不带 M1/M2）完全 0 变化，查下来是默认"原文查不到词频就不改"先把单字整窗弃权了——单字原文在词级表里必然查不到。**单字开关和 M1/M2 是绑在一起才有意义的**，我上轮汇报把它说成独立一步，口径不准，已在公共记录里更正。
2. 我的估算只数"没修好的错字"，没数"本来就对的字"。真实系统里凡是同音组内有更高字频候选就会改错正确文本，457 处误改全从这里来。这是方法错误，不是运气差：**今后任何"放宽某类改写"的预评估，必须把正确位点一起算进分母**。已在 E029 记录里写明更正段，并保留 E028 原文不覆盖。
3. 单字分数优势薄（刚过门槛那种），还会在竞争环节挤掉本来能改对的多字修复，所以改对字不升反降 52。这类二阶效应在单变量测试里看不到，说明"逐条件对照"的臂设计是必要的。

判断：单字这条路按证据先停，开关保持默认关。那 70.6% 的损失要收，需要的是词组/上下文级证据，而不是频率来源或窗口参数。仍未提交未推送。

发现什么问题：
1. 园长的判断被数据直接证实：程序过去缺的不是"再多一个改写理由"，而是"什么时候不该改"。加分项一放开，先受益的全是近音候选，而近音候选正是误改主力（纯改坏编辑 54→103/107）。

3. 我这轮又抓到并改正了自己两个口径错误：把 fuzzy 混进"AC 精确"（E030 也有这个错，已在 E031 记录里更正并单列近音类）；卫青族按出现次数计数出现过"15"这种误导性数字，已改成按词对计数（真实是 1/6，因为桑红阳→桑弘羊 一片里出现 15 次）。
