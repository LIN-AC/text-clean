# text_clean 算法复审与优化建议

日期：2026-11-02。范围：现有 C++ 工程、静态数据、回归脚本及上一轮结果。本轮提交分析报告，不修改生产算法；反例、插桩及对照实验全部位于 `.verify/algorithm_audit/`。

## 1. 结论与建议顺序

现有四段式架构可以保留，问题主要集中在第三段的候选生成和证据解释，没有必要整体换成复杂模型。

**推荐顺序：先补可靠词汇保护与评测，再做不改变决策的计算优化；之后统一候选窗口规则，最后用独立语料试验字符 N-gram。**

更简单的目标设计是：

1. AC 执行明确配置的精确动作。
2. 锁定跨度，确定可读上下文与可改范围。
3. 按候选词长度和拼音锚点提出少量候选；统一检查边界、原词保护、音近程度和分数；存在歧义时放弃。
4. 解决冲突并一次性输出，所有记录保留原文码点位置。

其中“候选提议”和“修改许可”必须分开：允许看到一个可能的候选，不意味着允许改写它。N-gram 只在第三段提供局部语言证据，不生成任意汉字替换，也不越过锁定范围。

| 方向 | 判断 | 原因 |
|---|---|---|
| 保留 AC、四阶段流程、静态先验、视频上下文生命周期 | 保留 | 已有明确职责及测试，重写收益小 |
| 先检索候选，后生成声调序列和查词频 | 优先实施 | 隔离实验输出一致，吞吐提高约 14.2% |
| 分开“合法词汇集合”和“纠错词频先验” | 优先实施 | 已复现“微星主板→微信主板”，当前未知词判定有漏洞 |
| 用统一边界检查替代多组窗口补丁 | 分阶段实施 | 降低重复生成和左右不对称，但要先证明行为等价 |
| 字符 2/3-gram 上下文否决 | 值得试验 | 可补充跨边界搭配证据；收益取决于独立、可信训练语料 |
| 词级 N-gram、整句 Viterbi 或 beam search | 暂缓 | 重新依赖分词，状态和参数显著增多，当前仅 10 个纠错目标不值得 |
| 从当前视频 ASR 直接训练在线 N-gram | 不建议 | 错误重复会形成自我强化，不能作为纠错正确性的独立证据 |
| 全词库扩成纠错候选、无约束逐字滑窗 | 不建议 | 增大误改面，违背“宁可漏改” |

## 2. 本次核查与证据

重新运行现有 CTest：**14/14 通过**。这不能说明算法已充分保守；新反例恰好暴露了现有测试的盲点。

### 2.1 新发现：动态上下文仍可覆盖正确的低频词

本次使用现有 CLI、原始数据实际运行：

| 原文 | 无上下文 | 标题“微信”、简介“微信使用教程” |
|---|---|---|
| 我买了微星主板 | 保持 | **我买了微信主板** |
| 请在微信里讨论微星主板 | 保持 | **请在微信里讨论微信主板** |
| 我在微信群里讨论微星显卡 | 保持 | **我在微信群里讨论微信显卡** |
| 支付保证金 | 保持 | 保持 |
| 提升个人威信 | 保持 | 保持 |
| 谈话核实 | 保持 | 保持 |

机制已定位：

- `data/dict.txt` 有“微星 3 n”；当前 `word_freq.txt` 没有“微星”。静态筛选把低频真实词移出了词汇视野。
- 原窗口于是 `fO=0`。微信候选最低词频为 3，距离为 2，静态分数为 `ln(4)-0.65*2-0.70≈-0.614`。
- 标题／简介合计出现两次“微信”，加分 `ln(2)≈0.693`，最终分数约 0.079，足以改写。并不需要 ASR 提供佐证。
- `tests/test_video_context.cpp` 把孤立“微星→微信”当作正向样例；这只在人工指定错误意图时成立。“微星”本来也是合法名称，不能用这一用例证明真实文本安全。

这不是需要再加一个“微星”特判的问题。根因是 **“不在经过筛选的词频表中”被近似成“原文缺乏合法词汇证据”**。任何低频品牌、人名、专业术语都可能受影响。上轮两篇正确文本零误改仍成立，但不能扩展到动态上下文的普遍安全性。

建议保留两份逻辑上独立的证据：

- `prior_frequency`：现有可比较频次，用于评分，不因为扩大词汇覆盖就改变尺度。
- `recognized_vocabulary`：经过清理的更宽词汇集合，只提供“原词可能合法”的保护信号。首先只查询完整原候选跨度，不把这些词全部塞进 AC，也不立刻改变分词词典。

第一版可采用简单保守规则：原词存在于保护集合时，不允许“仅靠动态加分”使一个原本不通过的候选通过。代价是漏掉部分合法词之间的真实同音错误，这与项目原则一致。不要宣称原始大词库全部可靠：其中低频噪声也可能阻碍召回，需按来源及独立开发集清理。

### 2.3 更简单的优化已经有实测收益

隔离原型仅移动计算顺序：先执行 `index.find_candidates`；为空则跳过，非空才执行 `frequencies.count(original)` 与 `to_toned_syllables(original)`。没有更改候选集合、评分公式或边界规则。

两个实验可执行文件用同一编译命令、同一模块库生成：

- 27 个既有注入样例 + 两篇正确文本 + 两篇固定 ASR，分别无上下文／合成上下文，**62 组 stdout 和 verbose stderr 全部一致**。
- 同一 2,227,480 字节文本，每臂 7 次交替执行取中位数。
- 当前顺序：**2.434 MB/s**；延迟计算：**2.780 MB/s**，吞吐约 **+14.2%**，耗时约 **-12.4%**。

这是局部实验收益，不是已合入性能，也不能外推到其他机器／词表。原型源码 `lazy.cpp`、原版对照 `current.exe`、实验脚本 `compare.py` 及全部计时留在 `.verify/algorithm_audit/`。这项优化优先级高于立刻添加 N-gram。

## 3. 当前算法具体问题

### 3.1 候选目标很少，但为大量无关窗口做通用查询

当前动作词表只有 10 条，静态词频有 96,451 条，二者不要混淆；AC 词表中的额外 Keep 条目通常没有拼音，不会自动变成纠错目标。

`PinyinInvertedIndex::find_candidates` 按“共享去重音节数”收集、排序，再截断为 64 个；扫描代码之后才过滤长度。当前小词表尚无明显截断损失，但扩展词表后，错长度条目可能挤掉正确长度条目。共享音节也不包含位置，重复音节只算一次。

改进：先按音节长度分桶，精确基音查找使用现成 `find_exact`，近音查询才访问相应桶。不要在发现精确候选后直接返回：精确候选也可能因原词保护或动作类型被拒绝，最终仍应统一比较所有允许候选。多音字查询必须统一使用读音集合；当前索引／首音节限制主要用首读音，而距离层使用多读音，存在检索与评分不一致导致漏召回的可能。需要单独测试，不能单纯把全局首音节过滤前移就声称等价。

### 3.2 窗口规则叠加，且左右不对称

当前窗口包括完整词、未知区内部窗口、未知区向前／向后跨词、2–4 个完整 token 拼接，以及两类边缘借字。最后靠 sort/unique 清理重复。

左侧借字不验证留下的前缀是否成词；右侧借字要求剩余部分能成多字词。这有实际保守作用，但不是统一的边界模型。右侧检查又只证明某个后缀前段在词典中，并未证明整个局部替换后的分词更合理。

建议先把已有窗口许可提取成单一边界检查函数并做等价测试，再考虑新的边界证据。不要一次重写窗口、分词、分数三处，否则无法知道收益和退化来自哪里。

### 3.3 声调距离与实际任务不完全一致

当前候选要求音节数量相同，却使用支持插入／删除的 Levenshtein，然后再做逐位置拼音字母距离限制。两套约束叠加，难以解释“为什么放行”。等长序列的 Levenshtein 仍可能通过一删一插获得较低分，它并不等价于逐音节替换成本求和。

若明确只支持等长 ASR 替换，可试验按位置累加成本并及早退出，通常比二维 DP 更简单。但这是**算法变化**，不是行为等价优化；必须与当前实现做差异审查。已有插删能力可保留在通用 edit_distance 库，流水线是否使用另行决定。

拼音字母编辑距离≤1也不等于真实语音相近。更可解释的长期方案是“基音相同／经真实 ASR 混淆统计确认的音节对／拒绝”三档；先不引入大量人工例外，也不要同时学习声母、韵母、声调等大量权重。首音节、polyphone 和音近过滤应复用一个一致的匹配判定。

### 3.4 频率比是启发式分数，不是已校准的纠错概率

`ln((1+fC)/(1+fO))` 在 fO=0 时给常见目标明显优势。拼接出来的多词窗口通常天然 fO=0，这不证明它是错误。目标热词下限3与普通词低频过滤进一步放大不对称。

现有动态模块实质上是“目标词领域加分”，并非完整视频词频模型。它不能把标题里的新词自动变成纠错目标，也不建模词序。当前机制比直接累加 ASR 词频安全，应保留上限，但不能替代词汇保护与局部证据。

### 3.5 重叠选择未比较全局最可信解释

`before()` 先按 begin 排序，之后贪心跳过重叠匹配。一个更早开始、分数较低的候选可能挡住更晚开始的强候选。同一窗口分数／距离相同则以 entry_id 决胜；词表顺序可能决定语义结果。

建议先做低复杂度保守改动：同分或近乎同分的不同替换拒绝决策；把相互重叠的候选作为小冲突组处理，证据不能区分时整个组保持原文。是否需要非零分差阈值由开发集决定。最大权重区间调度可最大化分数之和，但分数未校准时也可能鼓励多改，并不天然更可靠，暂不优先采用。

AC 的“左端优先最长匹配”及权威动作应维持兼容。另需明确“锁定所有 AC 命中的并集”还是“锁定选中的非重叠命中”：目前是后者，文档和重叠测试应描述清楚，不擅自更换策略。

## 4. 动态滑动窗口如何简化

推荐理解为 **候选驱动的有限长度扫描 + 独立边界许可**，而不是把所有字符任意拼接。

### 4.1 逐步落地方式

1. 每个原始 Han run 只解析一次字符读音和声调；按位置保存只读引用或紧凑音节 ID，避免每个重叠窗口重复复制读音 vector。
2. 预计算候选目标长度集合，当前主要是 2、3、4；不枚举词表没有的长度。
3. 用长度桶和可接受拼音锚点筛出候选起点。首音节非强制、polyphone 等配置必须进入判定，不能套一个无条件过滤。
4. 对每个 `(begin,length)` 只提出一次窗口，再查询候选。若需要不同来源许可，用标志位合并；保留当前普通窗口许可优先于边缘限制的行为。
5. 用统一函数检查 AC 锁、两端边界、是否切入可靠原词、局部重分词证据，再计算昂贵评分。
6. 低置信位置才允许边缘重分词；每次只比较候选周围有限区域，保持区域外分词与文本不变，不扩展成全句搜索。

若文本长度 N、目标长度集合为 L，则窗口上界可以控制在 O(N·|L|)，另加索引和候选评估成本。若默认首音节条件能安全用于锚点，则实际起点数远小于 N。不能把这个上界直接称为整体线性高性能，还需要考虑每个窗口的候选数、多音字读音数和分词查找成本。

### 4.2 不改变决策的优化清单

- 先做本次验证的延迟声调／词频计算。
- 未知区跨词循环直接按最大候选长度限制上下界，不先遍历大量必然超长的端点再由 add 丢弃。
- 相同 `(begin,end)` 在生成时去重；小长度集合可用每个起点的长度位图，避免全量 sort/unique。先检查内存占用和不同许可来源合并。
- `WordMaintainer::longest_match` 每次从最长长度倒扫并构造 substr；可先试 string_view 哈希查找或 trie。trie 可避免重复子串拷贝，但增加节点内存，需测启动/RSS，不能直接断言一定更快。
- 缓存规范候选静态频次、声调序列及 log 先验；当前声调序列已经缓存，词频对数还会重复求值。
- 在同一次 clean 内缓存相同原窗口的候选与纯音近结果；最终边界和上下文仍单独判定。有 N-gram 后不能把跨位置的最终分数也缓存复用。
- 复用 cleaner 和静态索引；视频上下文独立销毁。比为每句字幕启动一个进程更重要。CLI 本轮启动约70 ms，频繁逐句调用会吞噬文本算法优化收益。

## 5. N-gram 的收益与成本

### 5.1 它能补什么，不能补什么

字符 N-gram 可以提供候选附近的词序与搭配证据，例如比较“星主板”和“信主板”，以及替换前后跨词边界的连贯程度。它无需依赖固定分词，适合给现有拼音候选提供额外约束。

但 N-gram 不能创造缺失的纠错目标，不能恢复未生成的窗口，也不能自动区分罕见专名和错字。高频目标的内部片段也可能比低频正确词更常见，直接把语言模型分数加到已有词频比上，会重复奖励“常见词”，可能反而扩大误纠。

相关中文拼写纠错研究确实使用了 bigram/trigram、分词与平滑，但研究任务、候选空间和语料不同，不能把其结果当成本工程 ASR 的预期增益。[Xie 等，2015，原始论文](https://aclanthology.org/W15-3120.pdf)。

### 5.2 首选字符 trigram，回退 bigram；暂不做词级模型

| 模型 | 优点 | 主要问题 | 建议 |
|---|---|---|---|
| 字符 bigram | 小、简单、不依赖分词 | 上下文短，词内部频率偏置明显 | 作为回退与覆盖基线 |
| 字符 trigram | 能看到两字局部历史和跨边界组合 | 稀疏，领域术语仍缺失 | 优先离线试验 |
| 字符 4/5-gram | 更长局部搭配 | 模型更大、稀疏及语料要求更高 | 2/3-gram 有收益后再考虑 |
| 词级 bigram/trigram | 搭配解释直观 | ASR 错误导致分词漂移，OOV 多 | 当前不优先 |
| 拼音 N-gram | 可辅助音节序列判断 | 同音字候选音节相同，无法直接区分汉字 | 不作为主要判别模型 |

### 5.3 第一版只做否决，不救回原本被拒绝的候选

建议初始运行模式是观察模式：记录 N-gram 差分，不改变输出。独立开发集证明可靠后，只允许它否决现有算法本来会修改的候选；这样由它新增加的改写数严格为零，代价是可能降低召回。这是可解释的安全起点，而非承诺误改必然降到零。

对等长候选跨度 `[b,e)`，定义新旧序列 x' 和 x。阶数为 q 的前向语言模型只需重算：

`ΔLM = Σ(i=b … min(N-1,e+q-2)) [log P(x'_i | x'_{i-q+1:i}) - log P(x_i | x_{i-q+1:i})]`

在句首补统一 BOS，必要时计入句尾 EOS；不要让统计越过明确句界。以 q=3 为例，需要左侧最多2字符历史，并重算跨度及其后最多2字符。右侧字符虽然未改变，其条件概率会受改写影响，不能漏算。跨字幕 cue 使用前后文时，应由调用者提供上下文但限制只修改本 cue。

与词频避免重复计分：分别记录候选内部变化、跨左右边界变化；第一阶段主要观察边界差分。若只是“微信”内部统计比“微星”常见，不能据此认定“微信主板”正确。覆盖不足或只回退到低阶/OOV 时应视为无证据，不能将未见组合的零计数当作强否决或强支持。

第一版只保留一个经开发集标定的否决阈值及明确覆盖条件，不叠加多阶权重、领域权重、左右权重等大量自由参数。未来若要用 N-gram 正向提升召回，另设实验臂，仍需音近硬约束、合法原词保护与对不改方案的优势要求。

### 5.4 现有数据不足以证明 N-gram 有收益

本次审查数据：

- `word_freq.txt`：96,451 条；`dict.txt`：349,045 个唯一词。它们是词频列表，没有真实句子中的跨词联合统计。
- SUBTLEX 文件同样是词级频率／上下文分布计数，不能恢复词序条件概率。不要把词条按词频重复拼接后称作训练语料。
- 两篇正确文本只观察到 6,884 种 Han bigram、9,382 种 trigram。微信出现1次，微星／支付宝／华为出现0次；“微星主”“星主板”“信主板”“付保证”“保证金”等本次关键片段计数均为0。

这些计数仅用于数据充分性检查，不训练用于评测的模型。把这两篇文档用于训练后再测试其注入版本，会泄露正确答案；少量 ASR 即使规模更大也不等于可靠训练集。本轮因此不提供虚构的“N-gram 召回提升百分比”。

应另行获取许可清晰、经过清理的通用及字幕领域纯文本，按文档／视频划分训练、开发、盲测集，并排查近重复。当前两篇正确文本继续作为保留测试，不能混入训练。动态 ASR 最多保持目前受限的词项佐证，不把同一条错误重复训练成语言模型真值。

若语料规模值得引入成熟工具，可离线使用 KenLM 估计和平滑，运行时只加载小型模型查询。其官方文档支持 modified Kneser–Ney 估计与二进制模型加速加载；具体编译、模型大小及本机查询性能仍需实测，不能沿用工具论文的数字。[KenLM 官方说明](https://www.kheafield.com/code/kenlm/)。

## 6. 推荐的验证计划与取舍

### 第一阶段：修正安全目标，建立基准

- 新增合法低频品牌／人名／术语与目标词同音近音的负例，包含“微星主板”等；同一输入在相关、无关、误导、重复元数据下分别测试。
- 把带 Mask 动作的旧样例与纯纠错分开报告；“执行掩码”不应混入对外的纯纠错召回率。
- 修复“支付保护账户”样例的金标与跨度：现有正确句还要求多插一个“保”，不符合等长替换任务，不能拿它单独优化窗口。
- 同时统计新增误改处数、每万字符误改、正确句保持率、目标召回、目标之外的错误改写；目标命中不等于整句正确。
- 目前零误改仅覆盖约1.9万字符且样本集中，远不足以支持跨领域零误改结论。

### 第二阶段：独立验证实现优化

合入延迟计算，再逐项试验长度桶、预解码、有限长度窗口去重、分词查找结构；每项都要求现有语料与随机／极端输入的输出及匹配记录一致。记录初始化、上下文构建、热态 clean、整进程耗时、峰值 RSS、窗口数与候选数，不混淆启动和吞吐。

本轮实验仅覆盖62组行为一致性，没有证明所有输入等价，也没有做内存峰值验收；实际合入时需要补上这些检查。

### 第三阶段：算法替代逐项消融

建议保留这些独立实验臂：A 当前版；B 加原词保护；C B+统一窗口许可；D C+N-gram 仅否决；E D+受限局部边界放宽。另测“没有边界硬限制，仅靠 N-gram”作为风险对照，不作为默认上线方向。

每轮固定1–2个真实 ASR 视频人工核对所有改动，并逐轮累积金标；正向注入错误应来自真实混淆类型，不能只围绕目标热词造最有利样例。只要新增清晰误改就应分析原因并保守退回，不用总体召回提高掩盖。

**是否引入 N-gram 的最终标准**：独立盲测中能稳定阻止现有误改，召回损失可接受；或在不新增已确认误改的前提下恢复边界漏纠。若收益主要来自修复词汇保护、数据标签或候选生成，就不为此增加语言模型依赖。
